# Audit 2026-07-11 — confirmed findings and fix work order

Scope: everything merged in PR #6 ("embeddable DataTable and structured workbook tables") and PR #7
("complete spreadsheet setup and structure workflows"), audited at commit 64ace9e, plus a baseline
verification sweep. Method: 15 subsystem deep-read auditors; every finding below was independently
re-verified by 1-2 adversarial reviewers instructed to refute it (critical/high required two
confirmations); several were reproduced empirically. Two candidate findings were refuted and are
not listed.

Every finding below is REAL and must be fixed. Each fix must land with a regression test that
fails before the fix and passes after, except pure config/hygiene items where a test is
impractical.

## Fix mandates (read first)

1. **persistence must never destroy data (fixes the amplifier behind A1, A4, A31):**
   `loadWorkbook` currently maps any `migrateWorkbookModel` failure to `createBlankWorkbook()`,
   and the next autosave overwrites the stored JSON. Change the contract: on migration failure,
   quarantine the raw JSON (e.g. copy under a `<key>.corrupt.<timestamp>` storage key), surface a
   loud load error to the caller/UI, and never let an autosave clobber the quarantined original.
2. **command/loader validation parity:** anything the command layer commits must round-trip
   through `migrateWorkbookModel`. Prefer rejecting invalid commands at dispatch; the migrator
   stays as a backstop, not the primary validator.
3. Fixes must not regress the pre-existing feature set (pivots, ribbon selection-format
   summaries, fill handle, freeze panes, xlsx round-trip, autosave). The unit suite (1167 tests)
   and e2e suite (87 passing) are the floor.

## Findings

### A1 [CRITICAL] Content commands over a structured table's header desync table metadata; the saved workbook then fails migration on reload and the ENTIRE workbook is silently replaced with a blank one

- **Where:** `src/core/workbook/commands.ts:336`
- **Related sites:** `src/core/workbook/commands.ts:336`
- **Subsystem:** workbook-session
- **Defect:** cell.set is carefully table-aware (typing into a header row is rerouted to table.renameColumn at commands.ts:268-284), but the other content mutations are not: range.clear (line 336), range.fill (445), range.autoFill (457), clipboard.paste (497), clipboard.move (511), and clipboard.pasteMatrix (534) write straight through lib/workbook.ts with only read-only/permission checks. Clearing or pasting over a table header row changes sheet.cells while table.columns[i].name is untouched. migrateWorkbookModel requires sheet.cells[headerAddress] === column.name (migrateWorkbook.ts:429-431; same for totalsLabel at 433-435) and returns null for the whole workbook otherwise, and loadWorkbook (src/lib/persistence.ts:25) maps null to createBlankWorkbook(). Empirically verified with a temporary vitest file: on a session with a 2-column table, dispatching range.clear (mode contents) over the header row returns status committed, and migrateWorkbookModel(JSON.parse(JSON.stringify(snapshot.workbook))) === null; same for clipboard.pasteMatrix [["Renamed","Cols"]] at A1. Secondary effect: once the workbook is in this state, every id-generating command (table.create, table.resize, table.insertRows, columns.insert, sheet.duplicate) is rejected by the migrate-based invariant check in WorkbookSession.ts:679-694 with the misleading error TABLE_GENERATED_ID_INVALID.
- **Failure scenario:** User creates a table with headers (Insert > Table), selects row 1 and presses Delete (App.tsx handleClearSelection dispatches range.clear mode contents) or pastes over the header row. The command commits and autosave writes the workbook to localStorage (useWorkbookSession -> browserWorkbookStorage -> saveWorkbook). On the next page load, loadWorkbook -> migrateWorkbookModel returns null because the header cell no longer equals the column name, and the user's entire multi-sheet workbook is silently replaced by a blank one; the first edit then overwrites the stored JSON, making the loss permanent. Additionally, until reload, all table.create / columns.insert / sheet.duplicate commands fail with a bogus 'Generated structured-table IDs must be nonblank and unique' rejection.

### A2 [CRITICAL] Table row insert/delete rewrites references to cells below the table that never move, silently corrupting formulas

- **Where:** `src/lib/formulaReferences.ts:743`
- **Related sites:** `src/core/workbook/structuredTableRows.ts:286`
- **Subsystem:** formula-integration
- **Defect:** rewriteRowInterval() shifts any reference whose columns intersect the table with row >= insertion row, with no lower bound at the table's bottom edge (the sheetBounds field declared at formulaReferences.ts:39 is never read). But remapTableRows() in src/core/workbook/structuredTableRows.ts:396-416 only moves cells between the insertion row and table.range.end.row — cells below the table stay put (insertStructuredTableRows only requires the immediate expansion band to be empty via rowsAreEmpty, so data further below is allowed). The formula rewrite and the cell move disagree, so every formula pointing at data below a table in the table's columns is silently re-pointed one (or count) rows off on each table row insert/delete. Verified empirically: with a table spanning columns B..D and an insert at physical row 5, rewriteFormulaForRectangularRowEdit('=B20*2') returns '=B21*2' and '=SUM(C15:C30)' returns '=SUM(C16:C31)' while B20/C15:C30 never move; delete returns '=B19*2'. Named ranges below the table are shifted the same way via rewriteNamedRange (structuredTableRows.ts:337). Existing tests in formulaReferences.test.ts never cover a reference below the table bottom.
- **Failure scenario:** Sheet1 has Table1 in B2:D11 and a parameter cell B20 below it; F5 contains '=B20*2'. User inserts a table row (Table tab or DataTable add-row). F5 silently becomes '=B21*2', which points at an empty cell, so F5 now shows 0/blank and every downstream calculation is wrong; each further insert/delete drifts the reference further. No error is shown and undo history records the corrupted formula as a committed state.

### A3 [CRITICAL] Uncertain (network-failed) mutations are never reconciled: stale optimistic value permanently masks authoritative data and can overwrite a later committed edit

- **Where:** `src/table/remote/RemoteMutationController.ts:184`
- **Subsystem:** remote-table
- **Defect:** When source.mutate rejects with a non-abort error, the batch and its overlays are marked 'uncertain' and kept forever (lines 184-187): no query load/refresh ever reconciles them (only subscription pushes via acceptAuthoritativeRows do, and only for sources with subscription that happen to push that row). RemoteTableSession.readCell (RemoteTableSession.ts:989) always prefers the overlay over fresh canonical rows, and OptimisticOverlayStore.getLatest returns the last surviving overlay for the cell, so when a LATER edit to the same cell commits and its overlay is removed, the old uncertain overlay resurfaces. The batch also stays in `batches` forever, counting against maxPendingOperations (default 100), after which every edit is rejected with REMOTE_MUTATION_BACKPRESSURE until the session is restarted. Verified with a vitest repro: result {afterRefresh:'Grace', finalCell:'Grace', pendingOps:1} where the server value after refresh was 'Ada' and after the second committed edit was 'Marie'.
- **Failure scenario:** Source without subscription (e.g. plain REST): user types 'Grace' into a cell; the mutate HTTP call times out (server never applied it). Overlay goes 'uncertain' and stays. User hits refresh — server returns 'Ada', but the grid still shows 'Grace'. User types 'Marie'; that mutation COMMITS on the server; when its overlay is removed the old uncertain 'Grace' overlay becomes latest again, so the grid shows 'Grace' while the server holds 'Marie' — permanently, with pendingOperations stuck at 1 and no conflict/undo/refresh path to clear it. After ~100 such blips in a long-lived session, all further edits are rejected with REMOTE_MUTATION_BACKPRESSURE.

### A4 [HIGH] Command layer accepts inputs the workbook loader rejects (validation min>max, out-of-bounds named ranges/charts) — committing them bricks the saved workbook into a silent blank-on-reload

- **Where:** `src/core/workbook/commands.ts:386`
- **Subsystem:** workbook-session
- **Defect:** Several commands persist states that migrateWorkbookModel unconditionally rejects, with no validation parity: (1) range.validation.set (commands.ts:386) stores the rule verbatim via setCellValidation with no min<=max check, but migrateValidationRule rejects min>max (migrateWorkbook.ts:182); (2) namedRange.define (commands.ts:654) -> defineNamedRange (lib/workbook.ts:1051) never bounds-checks the range against the sheet, but migrateNamedRanges requires rangeInBounds (migrateWorkbook.ts:362); (3) sheet.chart.add (commands.ts:650) -> addChart only runs checkedRange/checkedCoordinate (non-negative integers), but migrateSheetCharts requires the range AND anchor in sheet bounds (migrateWorkbook.ts:324-325). Both (1) and (2) verified empirically: dispatch returns status committed and migrateWorkbookModel on the JSON-roundtripped snapshot returns null. Since WorkbookSession is the documented public embedding API (PR #6 'embeddable DataTable'), any host calling these with slightly-off arguments permanently destroys the persisted workbook.
- **Failure scenario:** An embedder (or programmatic integration) dispatches { type: "range.validation.set", rule: { type: "number", min: 10, max: 5 } } or { type: "namedRange.define", namedRange: { range: rows beyond sheet.rowCount } }. The command commits, the session autosaves, and on the next load loadWorkbook's migration returns null so the whole workbook — every sheet, table, and cell — is silently swapped for a blank workbook. Verified: both commands commit and the resulting saved JSON fails migrateWorkbookModel.

### A5 [HIGH] range.sort (and range.removeDuplicates) across a structured table body reorders cell data without reordering table.rowIds, silently rebinding every stable row ID to a different record

- **Where:** `src/core/workbook/commands.ts:469`
- **Subsystem:** workbook-session
- **Defect:** The design doc (docs/superpowers/plans/2026-07-09-workbook-structured-tables.md) states 'Row IDs survive insert, delete, physical sort, filter, resize, and undo while the workbook session exists' — i.e. a rowId stays attached to its record. Worksheet structural commands honor this (worksheetStructure.ts projectRowOperation rejects rows.insert/delete through a table body with TABLE_PARTIAL_STRUCTURAL_EDIT), but range.sort (commands.ts:469) and range.removeDuplicates (commands.ts:483) have no table intersection guard: sortRange physically permutes sheet.cells while workbook.tables[i].rowIds is untouched. Verified empirically: after range.sort desc over the body of a table seeded [Ann/30, Bob/40], cells.A2 becomes 'Bob' while tables[0].rowIds is unchanged — so the rowId that identified Ann's record now addresses Bob's data. All rowId-keyed operations (table.editCells, table.deleteRows, table.insertRows before/after, DataTable row identity held by embedders) now target the wrong records. removeDuplicates additionally shifts rows up within a fixed table range, pulling below-table data into the table body.
- **Failure scenario:** User selects a table's data rows and clicks Sort Descending in the Data ribbon (App.tsx dispatches range.sort on the raw selection). The sort commits with rowIds unchanged. A subsequent table.editCells for the rowId the host captured before the sort (e.g. from a DataTable row selection or drill-down) writes into a different customer's row — silent data corruption with no rejection or warning, and undo history records both states as valid.

### A6 [HIGH] table.resize with a totals row never moves the totals-row cells; subsequent totals toggle permanently deletes body data

- **Where:** `src/core/workbook/structuredTables.ts:306`
- **Subsystem:** structured-tables
- **Defect:** resizeTable changes the totals-row designation without moving the physical totals cells, corrupting the table body on grow and destroying body data on shrink + totals-toggle.
- **Failure scenario:** Table 'Sales' A1:B6 with totals row (=SUBTOTAL(109,B2:B5) in B6, set via table.setTotalsFunction). User resizes via the UI (App.tsx:2975-2980) to A1:B8: resizeTable (structuredTables.ts:244-315) only recomputes range/columns/rowIds and commits — no cells are relocated (contrast insertStructuredTableRows, which remaps the totals row after its internal resize). Result: the stale SUBTOTAL formula now sits INSIDE the body at row 6 (counted as body data), and the designated totals row 8 is blank. Shrinking (e.g. to A1:B4) is worse: a user data row becomes the 'totals row', and then unchecking Totals Row runs clearRowSlice (structuredTables.ts:362) on that row, permanently deleting the user's record (cells, formats, comments, hyperlinks).

### A7 [HIGH] Toggling the table header row shifts body formulas with naive reference translation and never rewrites external formulas pointing into the table

- **Where:** `src/core/workbook/structuredTables.ts:329`
- **Subsystem:** structured-tables
- **Defect:** shiftTableSlice applies copy-style reference translation to moved formulas and performs no workbook-wide rewrite for references into the moved region.
- **Failure scenario:** Table A1:B4 created with headerRow=false; D1 holds '=SUM(A1:A3)' and body cell B2 holds '=Z1+A2'. Enable the header row (UI checkbox, App.tsx:2981-2986): setHeaderRow shifts the whole table strip down one row via shiftTableSlice, translating moved formulas with translateFormulaReferences (structuredTables.ts:608-610), which shifts ALL relative references — verified: '=Z1+A2' -> '=Z2+A3' (Z1 is outside the table and never moved -> now reads the wrong cell) and '=Sheet2!B1' -> '=Sheet2!B2' (nothing on Sheet2 moved). Meanwhile D1's '=SUM(A1:A3)' is never rewritten, so after the shift it sums the header text plus the wrong body rows. Both directions of the toggle silently corrupt formula results; the row-insert path avoids exactly this by using rewriteFormulaForRectangularRowEdit, which setHeaderRow does not use.

### A9 [HIGH] Single-specifier structured references (Table1[#Data]/[#Totals]/[#All]/[#Headers]) are parsed as column names, making whole XLSX files fail to import

- **Where:** `src/lib/structuredFormula.ts:165`
- **Subsystem:** formula-integration
- **Defect:** parseStructuredReference only recognizes selectors inside nested brackets ('[[#Totals],[Col]]'). For the equally legal Excel single-specifier forms the content ('#Totals', '#Data', '#All', '#Headers') falls through to decodeStructuredHeader and is looked up as a column name. Verified: structuredFormulaToA1('=SUM(Table1[#Totals])') returns {ok:false, message:'Unknown structured table column #Totals'}; same for [#Data] and [#All]. On import, importStructuredTablesFromWorksheet (src/lib/xlsxTables.ts:133-134 for calculatedColumnFormula, :281-282 for totalsRowFormula) throws on the not-ok result, and importWorkbookFromXlsx (src/lib/xlsx.ts:83) propagates it — the entire workbook import fails, not just one table. Excel stores that structured text verbatim in xl/tables/tableN.xml. The import throws TABLE_FORMULA_REFERENCE_UNSUPPORTED and the whole file fails to open, even though every other sheet and table is fine.

- **Subsystem:** xlsx-roundtrip

### A13 [HIGH] Global XML element/attribute limits (100k/200k) reject legitimately-sized workbooks on BOTH import and export, breaking the documented huge-dataset / xlsx workflow

- **Where:** `src/lib/xlsxSecurity.ts:665`
- **Subsystem:** xlsx-security
- **Failure scenario:** parseSafeXml receives a single shared counter object (xmlCounts, created once at xlsxSecurity.ts:957) and is invoked for EVERY .xml/.rels part in the package (worksheets, sharedStrings, styles), incrementing counts.elements/attributes globally with no per-part reset. The default caps are 100_000 elements / 200_000 attributes (lines 30-31), and worksheet XML has ~1 <row> + N <c> elements (each cell also carrying r/s/t attributes). importWorkbookFromXlsx (xlsx.ts:73) calls validateXlsxArchive with no overrides and throws issueError on !ok (xlsx.ts:74). CONFIRMED empirically: a fflate-zipped package with one xl/worksheets/sheet1.xml containing 120k <c/> elements is rejected with issue.message 'The XLSX package exceeds the XML element limit.' A real ~12k-row x 10-col sheet (~120k cells) or any 100k-row file therefore fails to import. The same code runs on EXPORT: exportWorkbookToXlsx unconditionally calls patchNativeTableXml (xlsx.ts:65) -> validatedEntries -> extractValidatedXlsxEntries -> parseSafeXml with the same 100k/200k caps on ExcelJS's own serialized output, so a user who builds a >~33k-cell workbook in-app cannot export it either (throws 'exceeds the XML element/attribute limit'), losing access to their own data. Bundled fixtures are tiny, so tests stay green and hide the regression.

### A14 [HIGH] Stale-revision query response republishes the pre-flight 'before' snapshot, visually reverting mutations/subscription updates committed while the query was in flight

- **Where:** `src/table/remote/RemoteQueryController.ts:77`
- **Subsystem:** remote-table
- **Defect:** load() captures `const before = this.snapshot` (line 63) before awaiting source.query. If the response's revision compares 'older' than currentRevision, line 77 publishes `{...before, status:'ready'}` — but `before` is stale: any applyCanonicalRows/noteCurrentRevision/publishCanonicalState performed during the await (mutation acks in RemoteMutationController.execute, subscription rows-upserted) had already advanced the snapshot. The regression is sticky: currentRevision stays at the newer value, so the discarded response cannot be retried and later subscription events with an 'equal' revision are skipped; the page cache still holds the correct rows but nothing republishes them. The catch branch (line 106) has the same defect for failed refreshes. Verified with a vitest repro: after applying canonical revision '2' (salary 120) mid-flight, resolving the in-flight refresh with revision '1' left the published snapshot at revision '1'/salary 100. Fix direction: publish from `this.snapshot`/cache instead of the captured `before`.
- **Failure scenario:** Unprojected grid (paginationMode 'none'): a refresh is in flight; the user edits a cell and the mutation commits at revision 2 (grid shows the new value via publishCanonicalState). The refresh response, computed at revision 1, then arrives: compareRevisions(1,2)='older' and the controller publishes the captured pre-refresh snapshot — the user's committed edit disappears from the grid and stays gone (status 'ready', no error) until some unrelated interaction forces a new publish.

### A15 [HIGH] Infinite pagination: LRU eviction past maxPages silently drops the head pages and combine() presents the remainder as a contiguous list

- **Where:** `src/table/remote/RemotePageCache.ts:56`
- **Subsystem:** remote-table
- **Defect:** put() evicts the least-recently-used entry once size > maxPages (default 5). RemoteQueryController never calls get(), so lastUsed ordering equals insertion order and the evicted page is always the OLDEST — i.e. the head of an infinite list. combine() (lines 71-87) then flatMaps the surviving pages and rewrites pageInfo.loadedCount to items.length, so the session snapshot claims a contiguous list of N loaded rows that actually starts at row 51+. There is no mechanism to re-fetch evicted leading pages (infinite queries only go forward via 'after'). Verified with a vitest repro: after 6 loads of 1-row pages the snapshot items were ['row-2'..'row-6'] — 'row-1' silently gone. Also affects cursor mode, which accumulates pages the same way.
- **Failure scenario:** Infinite-scroll remote table with default cache (maxPages 5, limit 50): the user scrolls to load the 6th page. Page 1 is evicted; the snapshot now contains rows 51-300 reported as loadedCount=250 starting at index 0. The first 50 rows vanish from the grid, every remaining row shifts up by 50 (getRowIndex/selection indices now point at different records), and scrolling back up cannot recover them.

### A16 [HIGH] dispatch/updateOptions commit view states that make every subsequent getSnapshot() throw, permanently bricking the session

- **Where:** `src/table/local/RecordTableSession.ts:720`
- **Subsystem:** local-table
- **Defect:** updateViewState (lines 693-739) commits state without validating it against buildLocalRowModel's invariants, and getSnapshot() calls buildModel unprotected (line 320). buildLocalRowModel throws for: cursor/infinite pagination (localRowModel.ts:54-59), grouping or pagination combined with a getSubRows tree source (localRowModel.ts:48-53), and any sorting/filter/grouping/aggregate that references an unknown column id (validateRequestColumns, localRowModel.ts:313-325). Only the grouping+pagination conflict is guarded (lines 716-719, 232-244). Worse, dispatch() itself calls this.getSnapshot() for feature gating (line 410), so once bad state is committed, every feature-gated intent (including set-pagination/undo that could fix it) rejects with the same throw - the session is unrecoverable. updateOptions has the same hole: it never prunes state.sorting/filter/grouping/aggregates when the host passes a new columns array (lines 205-210).
- **Failure scenario:** (a) Host calls session.dispatch({type:'set-pagination', pagination:{kind:'cursor',...}}) - e.g. state persisted from a remote table - result is {status:'committed'}, then the next render's getSnapshot() throws 'Local tables do not support cursor pagination' and every later dispatch() rejects too; table UI crashes and cannot be repaired via the session API. (b) Tree table (source.getSubRows set): dispatch set-grouping or set-pagination offset commits, then getSnapshot() throws 'Tree expansion cannot be combined with grouping'. (c) User sorts by column X, host re-renders DataTable with X removed from columns (responsive column set) - updateOptions accepts it, next getSnapshot() throws 'Unknown column id: X'.

### A17 [HIGH] Editing a date/datetime cell stores an Excel serial number while the whole local stack (filter/sort/group/display) expects ISO strings - silent data corruption

- **Where:** `src/table/local/RecordTableSession.ts:1187`
- **Subsystem:** local-table

### A18 [HIGH] Table sort and delete-rows move cell data but leave per-cell read-only protection behind, silently unprotecting data and locking wrong cells

- **Where:** `src/core/workbook/structuredTableRows.ts:419`
- **Subsystem:** workbook-table-session
- **Defect:** remapTableRows (structuredTableRows.ts:394-426), the physical row-movement engine for table.sort (line 222), table.deleteRows (line 140), and table.insertRows (line 87), remaps only cells, formats, validations, comments, and hyperlinks. The table session exposes readOnly as first-class per-cell metadata (WorkbookTableSession.ts:447 editable, :490-497 update-cell-metadata readOnly -> range.readOnly.set -> lockedCells), and getCellReadOnly (lib/workbook.ts:206-210) honors lockedCells even on unprotected sheets.
